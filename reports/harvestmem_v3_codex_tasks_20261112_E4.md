# HarvestMem v3：E4 任务单（给 Codex）

日期：2026-11-12。依据：E3 原始轨迹（`results/harvestmem_v3_E3/{A,D,E}/count/ep*/trace.jsonl`），指挥者已逐条复核。

## 0. 本轮目的

路线已定：**任务层决策由显式记忆（跟踪器）做出，并用结构方式执行，不再要求 VLA 自己"听懂"何时停。** VLA 只负责摘一颗、放一颗。

E4a 只回答一个问题：Count 中，跟踪器判定"凑够 N"后，由脚本动作接管（回到 rest、张开夹爪、保持静止），能否把"凑够了但没停下"的回合变成成功？本轮不训练、不改任务、不改跟踪器。

## 1. 指挥者从 E3 轨迹核实的事实（写进报告前先用你的脚本复算一遍）

1. **起步失败**：观察段结束后，VLA 没有离开 rest，在 rest 静止满 40 步，被环境判为"完成信号"，此时篮中 0 颗，回合在第 69–105 步结束。
   - 发生次数：A 8/40，D 18/40，E 5/40。
   - 有 4 个回合三个臂都出现起步失败：207、218、222、237。
   - E3 报告把这些回合归入 never_pulled 和"低层执行问题"，归类不对：这是起步决策失败。
2. **凑够 N 但不停**：
   - 凑够 N 的回合数：A 11/40，D 13/40，E 15/40。这些回合在凑够 N 之前都没有掉果。
   - 结局：之后全部是 overpick，只有 D 的 204 和 E 的 209 是耗尽预算。
   - 回合编号：
     - A：209、211、212、214、225、226、229、230、234、235、238
     - D：201、204、206、212、220、224、225、228、229、231、234、235、238
     - E：204、209、211、214、215、217、219、220、225、226、229、232、234、235、236
3. **时间余量**：
   - 第 N 颗入篮后 4–6 步，跟踪器的 `oracle_phase` 变为 `return`。
   - 之后 60–80 步，VLA 才拉下第 N+1 颗，触发 overpick。
   - 所以强制停止有足够的余量。
4. **专家的放果方式**：`solver.pick` 的放果是带果移到 `home`（rest 位姿）后再张爪。因此每放完一颗，机器人本来就在 rest 附近，"停止"只需留在原地并静止。
5. **run_e3.py 的两个指标错误**：
   - `target_follow` 只统计与 `target_selected` 同一行的脱落（`j == i`），结果恒为 0%。
   - `return_follow` 在没有 return 起点时记为 False，把没凑够 N 的回合也算进了分母。
   - 正确数值见第 3 节的参考值。

## 3. E4-0：决策层指标脚本与 E3 勘误（只用 CPU）

新建 `scripts/harvestmem_v3/decision_metrics.py`，输入为任一结果目录（E3 或 E4），对每个臂和任务输出下列指标。

**Count：**

| 指标 | 定义 |
|---|---|
| 起步失败 | `reason == finish_signal`，且 `n_in_basket == 0`，且 `steps < 200` |
| 凑够 N | 任一行 `n_in_basket >= N` |
| 凑够 N 后正确停止 | 凑够 N 的回合中 `outcome == success` 的比例 |
| 凑够 N 后多摘 | 凑够 N 的回合中 `reason == overpick` 的比例 |
| 中途少摘就停 | `reason == finish_signal`，且 `0 < n_in_basket < N` |
| 每次拉下入篮率 | 机器人拉下的果子中，300 帧内进入篮子的比例 |
| 目标一致率（所有臂） | 每次机器人拉下果子时，被拉下果子的 slot 是否等于此前最近一次 `target_selected` 的 `oracle_target_slot`。D、E 臂的跟踪器也在运行，这个指标衡量它们的摘取顺序是否与规则一致 |
| 执行失败 | `robot_drop`、`tcp_stuck_300`（沿用 E3 定义）、未凑够 N 而耗尽预算、除起步失败以外的 never_pulled |

**Occluded：**

| 指标 | 定义 |
|---|---|
| 拉对比例 | 被拉下的果子中初始为熟果的比例 |
| 生果入篮率 | 回合中有生果入篮的比例 |
| 目标一致率 | 同 Count |
| 成功率 | 沿用 E3 |

**Count 失败归类**：每个失败回合必须归入且只归入一类，"决策失败"或"执行失败"：

- 决策失败：起步失败；凑够 N 后多摘；凑够 N 后耗尽预算；中途少摘就停。
- 执行失败：其余情况。

用这个脚本复算 E3，写出 `reports/harvestmem_v3_E3_erratum.md`。

复算结果与指挥者的参考值相差超过 1 个回合时，停下汇报，不要自行调整定义。参考值：

| 臂 | Count 每次拉下入篮率 | Count 目标一致率 | Occluded 目标一致率 | Occluded 生果拉下 |
|---|---|---|---|---|
| A | 83% | 92% | 26% | 26/58 |
| D | 88% | 98% | 9% | 28/43 |
| E | 82% | 96% | 38% | 28/56 |

勘误文件要说明两点：
- E3 按预登记规则得出的结论（A 两个任务都低于 40%）照原样保留。
- 但"低层执行问题"这个归因不完整：Count 的失败中，决策失败占多数（起步失败 + 凑够 N 后不停）。

## 4. E4a：跟踪器触发的强制停止（Count）

### 4.1 实现

在 `eval_episode.py` 新增开关 `--enforce-stop`（默认关闭），再加一个只用于冒烟的 `--debug-stop-at-step K`（默认 None）。

**触发条件**（开关打开、任务为 count 时才生效）：
- 每个环境步之后检查，包括 16 步动作块内部的每一步；
- `timestep >= 30`，且本步跟踪器输出 `phase == "return"`，且本步快照 `n_in_basket >= N`；
- 调试开关下，改为在第 K 步无条件触发。

**触发后（锁定，不再解除）：**
- 立即中断当前动作块，此后不再调用 `add_buffer`、`infer`。
- 七个关节从当前位置线性插值到 `keyframes['rest'].qpos[:7]`，每步每个关节的变化不超过 0.01 rad，夹爪动作为 1.0（张开），`guard=False`。
- 到位后持续发送 rest 关节目标、夹爪张开，直到环境结束回合。
- 每个脚本动作都写入 `actions.jsonl`，并标记 `"source": "stop_primitive"`；VLA 动作标记 `"source": "policy"`。
- 触发后 300 步内回合仍未结束，记 `stop_primitive_timeout`。

**`result.json` 新增字段**：`enforce_stop`、`stop_trigger_step`、`stop_trigger_n`、`stop_arrive_step`、`stop_end_step`、`stop_primitive_timeout`。

触发只依据跟踪器和快照，这里用的是**真值跟踪器（上限）**，报告中要明确写出这一点。

### 4.2 冒烟（必须全部通过才能开始正式运行）

1. **调试触发**：K0 在 count ep200 上加 `--debug-stop-at-step 200`。要求：
   - 回合以 `finish_signal` 结束，而且是因为篮中数量不等于 N 才判失败；
   - 从触发到结束不超过 300 步；
   - 截取触发前后的视频帧，确认机器人回到 rest 后静止。
2. **真实触发**：K0 加 `--enforce-stop`，跑 count ep220、ep235、ep206。
   - 这三个回合在 E3 中凑够了 N，但闭环有随机性，这次未必凑够。
   - 只要有一个回合触发，就检查以下四项：`stop_trigger_n == N`、没有 overpick、`stop_end_step - stop_trigger_step <= 300`、结局。
   - 三个都没触发，就再从第 1 节 D 的列表中依次补跑，直到出现一次触发。
3. **开关关闭**：K0 不加开关跑 count ep200，确认 `actions.jsonl` 中所有动作都是 `"source": "policy"`，且没有出现 `stop_*` 字段。

### 4.3 正式运行

新建 `scripts/harvestmem_v3/run_e4.py`，结构仿照 `run_e3.py`，输出到 `results/harvestmem_v3_E4a/`。

- **任务与回合**：只跑 Count，dev 200–259，共 60 个回合。
- **臂**：

  | 臂 | checkpoint | 记忆 | 强制停止 |
  |---|---|---|---|
  | D | K0 | uniform | 否 |
  | DR | K0 | uniform | 是 |
  | E | NM | none | 否 |
  | ER | NM | none | 是 |
  | A | SG + 跟踪器子目标 | uniform | 否 |
  | AR | SG + 跟踪器子目标 | uniform | 是 |

  - 不开关的臂要在同一版代码下重跑，不复用 E3 的结果。
  - 同一 checkpoint 的两个臂共用一组服务通道，队列按（回合，臂）交错排列，让两臂的运行时段一致。
- **GPU 分配**：SG 用 0–1，K0 用 2–4，NM 用 5–7。每个通道 1 个服务、1 个客户端。
- **预计耗时**：每回合约 50 秒，360 回合，共约 40–60 分钟。

### 4.4 预登记（正式运行前不得修改）

**工程门槛**（任何一条不满足，都只算工程问题：停下排查，只重跑 R 臂）：
- R 臂中 `overpick` 为 0；
- 所有触发回合 `stop_trigger_n == N`；
- 所有触发回合在 300 步内结束，且结束原因为 `finish_signal`。

**预测**（依据 E3：D 在 40 个回合中有 13 个凑够了 N）：
- DR 的 Count 成功率 ≥ 20%（60 个回合中至少 12 个），且高于 D。
- ER、AR 作为次要结果，按同样口径报告。
- 起步失败的回合数不受强制停止影响，预测 DR 与 D 相近。

**判定：**
- 工程门槛通过，且 DR ≥ 20%：结构化停止有效，进入 E4b。
- 工程门槛通过，但 DR < 20%：比较 D 本轮与 E3 的"凑够 N"比例。如果 D 本轮也明显下降，说明是闭环方差。只汇报，不调参数，停下。
- 每个臂都报告成功数及 Wilson 95% 区间。DR 与 D 按回合配对，报告四格表：两者都成功、只有 DR 成功、只有 D 成功、都失败。

## 6. E4b 预告：规划器送到目标前（这轮只写设计说明）

**设想**：跟踪器每选中一个目标（包括观察段后的第一个），先由专家规划器把夹爪送到该果的预抓取位姿，再交给 VLA 完成接近、抓取、拉下、搬运、放果。
- 这样可以同时解决起步失败（第一个目标由规划器出发）和 Occluded 的选错果问题。
- 停止仍沿用 E4a 的强制停止。

**设计说明需要回答：**

1. **规划器与环境**：如何在评测环境上构造与示范相同的规划器。
   - 示范用的参数：`FruitPickSolver(env, step_fn, ik_mode="canonical_v31", ik_seed=0, ik_candidates=64)`，见 `scripts/harvestmem_v3/run_episode.py` 第 139 行。
   - `step_fn` 要接到 `Episode.step`，让轨迹、跟踪器、视频照常记录。
   - 障碍物刷新方式与示范保持一致。
2. **预抓取位姿与交接时机**：预抓取位姿按 `solver.pick` 的 reach 阶段计算（果子当前位置，`PRE_GRASP = 0.12`）。说明在哪个事件把控制交回 VLA，以及在哪个事件重新交给规划器。
3. **记忆帧**：规划器运动期间的画面是否照常放进 VLA 的记忆缓冲区，以及理由。
4. **规划失败**：规划失败时怎么处理（建议交回 VLA 并记录），以及要报告哪些指标。
5. **分布偏移检查**：交接点的状态是否处在 VLA 的训练分布内。
   - 建议的检查方式：在 dev 专家示范的 reach 结束点上，用现有 `open_loop.py` 计算 VLA 动作与专家动作的误差比，与 E2 的整体误差比做比较。
6. **臂与任务**：拟评测的臂（如 K0+规划+停止、NM+规划+停止），覆盖 Count 和 Occluded；附预计耗时。
